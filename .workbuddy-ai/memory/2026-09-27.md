# 首屏视频循环卡顿 —— 诊断与解法

用户反馈"播放结束和重新播放中间的卡顿，视觉体验很一般"。实测后确认是**两个独立问题叠加**，
只解决任一个都不会变丝滑。

## 诊断方法（可复用）

1. **解析 MP4 box 结构**（纯 Node，不需要 ffmpeg）：下载视频后遍历顶层 box + mvhd/stts/stss。
   发现：`moov` 在 `mdat` **之后**（未做 faststart）、时长 8.042s / 24fps / 193 帧、
   **关键帧只有 2 个**（第 1、120 帧，第二个 GOP 近 3 秒长）。
2. **Playwright 实测 loop**：rVFC 记录每帧 mediaTime + 监听 `waiting`/`seeking`。
   循环点稳定出现 `seeking` + `waiting`，墙钟间隔 **64ms / 83ms**（正常帧间隔 41.7ms）。
3. **canvas 取首末帧算像素差**：末帧 vs 首帧 = **6.28**，而相邻帧只有 0.37~1.59
   → **素材本身首尾就不接**（同一场景不同时刻：水柱宽度、鱼的位置、底部光斑都变了）。

结论：① 是技术层面（`loop` 的实现是 seek 回 0 + 解码器重置）；② 是素材层面，
**任何"让 loop 更快"的优化都救不了 ②**。

## 解法：双 video 交叉溶解

一个 video 播到 `dur - 1.2s` 时，另一个从 0 开始播并淡入盖住前者。停顿被盖住，跳变被溶解。

**踩过的坑（都是真会再犯的）**：

- **两个类必须分开**：`is-front`（只管 z-index）+ `is-visible`（只管 opacity）。
  旧层保持 opacity 1 不动、新层从 0 淡入，数学上才是干净的交叉溶解。
  若让两层同时淡入淡出，中间点会透出 25% 的兜底背景，**画面发暗**。
- **等新层渲染出第一帧再淡入**（`requestVideoFrameCallback`）。否则 seek 期间它是空白，
  淡入会变成「一块空白逐渐盖住旧画面」。600ms 兜底防它永远不淡入。
- **swap 定时器要从"真正开始淡入"那一刻起算**，否则两层会同时半透明。
- **等 `canplaythrough` 再起播**（移除 `autoPlay` 属性）。实测边下边播会反复 `waiting`。
- **z-index 陷阱**：元素一旦有 z-index，就会盖住 `z-index: auto` 的定位元素 ——
  `.vh-scrim` 必须显式抬到 video 之上，否则压暗层被视频吃掉。
- 对已在 0 的元素写 `currentTime = 0` 会触发一次无谓的 `seeking`，加条件跳过。

## 实测结果（用本地视频排除网络变量）

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 播放中停住 | 108 次 / 20s | **1 次**（起播瞬间） |
| waiting | 13 次 | 3 次（全在 t=0、rs=4 的**不可见层**上） |
| 交接次数 | 0（根本播不到） | 3 次，间隔 6907ms（理论 6.84s） |
| 旧层 opacity | — | 全程 1.00 |
| 新层 opacity | — | 0.01→1.00 平滑 13 步 |

交接中点实拍：看不出两层叠加，无发暗、无重影。

## 修正：faststart 的收益别说过头（我第一遍说错了）

我第一遍写的是"moov 在 mdat 之后 → 必须整段下完才能播"。**这是错的**，实测推翻了它：

- CloudFront **支持 Range**：`Accept-Ranges: bytes`，请求 `bytes=7608723-7611845` 返回
  **206 + 3123 字节**，0.68s。
- 浏览器**真的会主动去取尾部**。实测它发的请求序列：
  `bytes=0-`（试探）→ 中止 → `bytes=7602176-`（取 moov，9670 字节）→ `bytes=32768-`（取画面）。
- 顺带解释了之前一直看到的 `net::ERR_ABORTED`：那不是"重试失败"，
  是浏览器**故意中止**那个开放式请求，改发精确 Range。

所以准确表述是：**不用下完，但要多跑一趟往返**。
实测从发请求到能播用了 **1410ms**，其中约 1 秒花在那趟尾部请求上；
moov 前置（faststart）后一次请求就够，约 350ms 能播。

**"必须下完才能播"只在服务器不支持 Range 时成立**（返回 200 而非 206）。
某些简单静态托管、`file://` 本地打开、部分老式服务器属于这种。

**关键修正：faststart 不解决循环卡顿。** 循环卡顿来自 `loop` 的 seek 机制 + 素材首尾不接，
那是交叉溶解解决的。重编码三件事各自治什么：
- 降码率（7.6 → 2~3 Mbps）→ **治播放中卡顿**（最关键，中国网络下这是主要矛盾）
- 缩短 GOP（关键帧 2 个 → 每 1~2 秒一个）→ 治 seek 精度
- faststart → 首帧早约 1 秒（锦上添花，不治卡顿）

## 第二次修正：单帧截图证明不了"溶解自然"（我上轮验证方式错了）

用户反馈：**"每次重复播放的间隙那种闪回的感觉还是不舒服"** —— 即 1.2s 的交叉溶解
虽然把"跳变"变成了"渐变"，但看着像闪回。

**根因**：溶解期间两层画面**各自动着**，运动互相打架。旧层在末尾（水柱宽、鱼分散），
新层在开头（水柱窄、鱼集中），1.2 秒里观众同时看到两个不同时刻的画面 → 大脑识别为"重影/闪回"。

**我上轮的错误**：用"交接中点的**单帧截图**看不出两层叠加"来证明方案有效。
单帧当然看不出 —— 静态画面里 50/50 混合只是一张图。
**双重曝光的难受来自「持续时间」和「两套运动」，这两个都只在动态里存在。**

**改法**：`FADE_SECONDS` 1.2 → **0.4**（剪辑里用来消掉跳切的快速叠化区间）。
缩短的是"暴露时间"，不是"强度"（强度由素材首尾差异决定，恒为 6.28）。

**结论**：素材首尾不接时，任何过渡方式都只能"掩盖"不能"消除"。彻底解法只有重编码素材
（末尾与开头做交叉溶解烘焙成真正无缝的循环，或正放+倒放 ping-pong）。

## 怎么拿到 ffmpeg（三条路，最后一条成了）

1. `npm i ffmpeg-static` → 二进制被 install-scripts 策略拦，没有 exe
2. GitHub 直链下载（`ffmpeg-static` 的 release，29.6MB）→ **中国网络超时**，
   断点续传 7 分钟只下了 2.3MB
3. ✅ **`@ffmpeg-installer/ffmpeg`（走 npm registry + npmmirror 镜像）→ 5 秒装完**
   - `npm i @ffmpeg-installer/ffmpeg --registry=https://registry.npmmirror.com`
   - 二进制在 `node_modules/@ffmpeg-installer/win32-x64/ffmpeg.exe`
   - **结论：要二进制工具优先找 npm 包形式，别去 GitHub release**

注意：这个 ffmpeg 是 2018 年的构建（N-92722），**没有 `xfade` 滤镜**（4.3+ 才有），
但有 `blend` —— 交叉溶解用 `blend=all_expr='A*(1-T)+B*T'` 即可。

## 重编码命令（可复用）

```bash
ffmpeg -y -i in.mp4 -filter_complex \
"[0:v]trim=start=1:end=7.04,setpts=PTS-STARTPTS[body];\
[0:v]trim=start=7.04:end=8.04,setpts=PTS-STARTPTS[tail];\
[0:v]trim=start=0:end=1,setpts=PTS-STARTPTS[head];\
[tail][head]blend=all_expr='A*(1-T)+B*T'[xf];\
[body][xf]concat=n=2:v=1[v]" \
-map "[v]" -an -c:v libx264 -crf 24 -preset slow -g 48 \
-movflags +faststart -pix_fmt yuv420p out.mp4
```

**原理（容易想错，记下来）**：
设原时长 D、溶解 F。新视频 = `[F, D-F] 主体` + `F 秒溶解段`，长度 D-F。
溶解段 = `tail[D-F, D]` 淡出、`head[0, F]` 淡入。
于是 **溶解段末帧 = head 末帧 = 第 F 秒画面**，而**新视频首帧 = 主体首帧 = 第 F 秒画面** → 接上。
（第一版我想错了：把溶解段接在末尾但保留开头，那样末帧=第F秒、首帧=第0秒，还是不接。）

### 迁移前发现的三处真缺陷（都是既有代码）

1. **`ai-navigator` 工具网格每次输入都重放**：内联
   `animation: content-rise 400ms … ${i*25}ms both` —— React 在 `i` 变化时重写
   style 字符串，浏览器就重启动画。而且**内联样式优先级高于样式表**，
   `@media (prefers-reduced-motion: reduce)` 覆盖不掉它（真无障碍缺陷）。
2. **`profile` 的 `.ac-cut` 把 `opacity: 0` 写在 CSS 里** → JS 一旦没跑，
   SHOT 02–04 三屏内容**永久不可见**。延迟也是手写公式 `120 + idx*70ms`。
3. **死代码**：`.reveal` 类全项目 0 处使用（App.tsx 里那个 IntersectionObserver
   是空转）；`.route-mobile-ready` 从未被使用；`.page-shell > *:nth-child(2..5)`
   从来没生效过（`main > *` 实际只有一个子节点）。

### 四个坑（已写进技能 `animejs-motion-layer`，此处只记结论）

1. **anime.js 的 from 值不是创建时就落地**，要等引擎首次 tick → 元素先完整显示
   一帧再跳成 0。实测：首帧 `k/t/n` 全 `1.000`，下一帧才 `0.094`。
   修法 = 创建动画前手动写内联初始态 + 用 `useLayoutEffect`（绘制前）
2. **动 `transform` 会整个覆盖元素自带的 transform**（`skewX(-5deg)`、
   Tailwind `hover:-translate-y-0.5`）。改用**独立的 `translate` 属性**
   + 自定义属性 `--m-rise`（CSS 工具类 `.m-rise`）。已验证动画后
   `.ac-shottitle` 的 matrix 仍含 skew 分量
3. **祖先带 transform 会改 fixed 后代的包含块** → 容器只能动 `opacity`
   （opacity 只建层叠上下文，不建包含块）。容器从 `0.3` 起淡入而非 `0`，
   否则把容器内的 `.ac-flash` 一起乘暗
4. **`querySelectorAll` 不含 root 自己**，要动 root 得直接传给时间线

顺带修掉自己引入的一个 bug：`.ac-flash` 和 `<RouteCut>` 同时用了
`key={activeRouteItem.id}` → React 重复 key 警告（308 条 console error）。
