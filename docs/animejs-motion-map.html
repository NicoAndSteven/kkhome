五个误判，全是我的用法错，不是 anime.js 的限制。这段值得看，因为它就是接入时最容易踩的坑：

  • createLayout — 我读 transform 判定"没动"，实际它动的是独立的 translate 属性。这正是上一轮动效层里我踩过的同一个坑。
  • scrambleText — 属性名必须写 textContent。写 text 时静默无效、不报错。
  • createDrawable — 必须把 createDrawable() 的返回值交给 animate()，传选择器会丢掉上下文。
  • createMotionPath — 返回的是普通对象，我却在 SVG 元素上读 computed translate，量错了对象。
  • createDraggable — 我把 container 设成了元素自己，可移动空间为 0，所以"拖不动"。

共同点：五项全部静默失败。没有异常、没有警告、控制台干净。这类 API 不能靠"跑起来没报错"验收，必须量最终数值。

一个必须知道的前提：anime.js v4 的 API 和 v3 完全不同。v3 是 anime({...})，v4 是 animate() / createTimeline() / createScope()。 网上绝大多数教程、StackOverflow 答案仍是 v3，照抄必错且不报错。仓库里已用 eslint 把 animejs 限制为只能从 src/core/motion.ts 导入，这个护栏要继续保持。

02能力地图

按「CSS 能不能做」分四类，而不是按 API 罗列

按 API 列清单没有决策价值。真正决定"要不要上"的问题只有一个： 这件事 CSS 能不能做？能做的，上 anime.js 就是净损失（性能降级 + 多一套实现）。

① 连续性数值映射 CSS 做不到

输入是连续量（指针位置、滚动进度、音频振幅、拖拽速度），输出要跟着连续变。CSS 只能表达离散状态（:hover、class 切换），没有"按比例"这回事。

API createAnimatable · onScroll(sync) · createDraggable · damp/lerp/mapRange

② 运行时才知道的编排 CSS 做不到

元素数量、文字字数、列表长度来自接口或用户输入。CSS 的 animation-delay 是静态的，写不出"按实际数量逐项错峰"。

API stagger(grid/from) · splitText · createTimeline

③ 几何与拓扑变换 CSS 做不到

位置/尺寸变化后平滑接续（FLIP）、路径描边生长、形状形变、沿曲线运动。CSS 没有 FLIP，没有路径插值。

API createLayout · createDrawable · morphTo · createMotionPath

④ 可中断 / 可回退 CSS 做不到

动画进行到一半要改方向、要取消、要退场。CSS 一旦开始就跑完，没有"中途接管"的接口。

API Timeline.pause/play/revert · createScope 自动 revert · createSpring 可重定向

反过来：这些交给 CSS，不要动

状态过渡

:hover / :focus / :active。CSS 能做，浏览器优化最好，且 JS 未加载时依然可用。

本仓库 120 处 transition-premium + 29 处 transition:

纯装饰循环

骨架屏微光、录制点闪烁、跑马灯。无输入、无编排、无中断需求 —— 上 JS 只会让主线程多一件事。

本仓库 skeleton-shimmer ×31
ac-rec-blink · vh-rec · ac-tape-run

能写成 keyframes 的定长动画

时长固定、元素数量固定、不需要中途接管。写成 CSS 跑在合成器线程，比 rAF 更稳。

本仓库 剩余 keyframes

一句话判据：问"这个动画的输入是什么"。 输入是 CSS 状态（hover / class）→ 用 CSS； 输入是 连续量或运行时数据（指针、滚动、字数、列表长度、接口结果）→ 用 anime.js。 输入是 无（纯装饰循环）→ 用 CSS。

04建议路线

按"可见收益 ÷ 风险"排序，不是按技术含量

阶段做什么为什么排这儿风险
P0 删 5 个死 keyframes；把 9 处 animate-[...] 和 5 处 mini-bar 内联手算迁到 useStaggerIn 纯减法 + 修既有缺陷（内联样式绕过 reduced-motion）。不新增任何东西，先把地基扫干净。 低
P1 FoodWheel 改 spring + draggable 单点、独立、用户能立刻感觉到。转盘是游戏，手感就是它的价值。 中
需要处理指针与旋转角换算
P2 Sheet / Drawer 的退场时间线 修的是真实缺陷：现在关掉是硬消失。三处共用一套 useOverlayTimeline。 中
卸载时机要处理干净，否则会留残影
P3 ai-navigator + wish-wall 上 createLayout 列表筛选/排序是这两个页面的主要交互，FLIP 让"重排"从瞬移变成移动。但要注意：它会把元素临时设成 position: absolute，容器必须有确定的定位上下文。 中高
要先验证不破坏现有网格布局
P4 真实音频频谱（AnalyserNode + createAnimatable） 从"假动画"变"真信息"。AudioContext 已经在项目里了，只差一个 Analyser。 中
注意 iOS 音频策略与性能
P5 逐字入场 + 数字滚动 + useTilt 迁移 观感提升明显，但属于"锦上添花"，且 splitText 有无障碍细节要处理。 低

如果只做一件事，做 P1。转盘是唯一一个"动效质量 = 产品价值"的地方 —— 用户拨它就是为了那个手感。其余多数地方是"更好看"，只有它是"更好用"。

05诚实的边界

三个我确认过的限制，以及三个我没验证的

确认的限制

它不是组件库

没有渲染、没有状态、没有生命周期。它只能让已经存在的 DOM 动起来。所以"替换所有组件"这个说法本身不成立 —— 能替换的是动效的实现方式。

70 个 tsx 里绝大多数与它无关

接管不了伪类

:hover / :focus 只能留在 CSS。硬改必然产生两份实现。

162 处状态过渡保持不动

失败是静默的

本次实测中 5 项用法错误全部没有报错。不能用"跑起来没异常"验收，必须量最终数值。

控制台错误 0 ≠ 用对了

我没验证的

  • createLayout 的 enter / leave。我验证了重排（swap），但没测元素增删的进出场。而 P3 恰恰要用这个 —— 落地前必须先单独验证。
  • 大量元素下的性能。探针最多测了 12 个元素。313 条工具的网格是另一个量级，需要单独压测。
  • Safari / Firefox 行为。本次只在 Chromium 实测。上一轮 backdrop-filter 的教训说明跨浏览器差异是真实存在的。

还有一个前置问题必须先解决。仓库里 src/core/motion.ts 已经是 anime.js 的唯一入口，eslint 有 no-restricted-imports 护栏。 这次改造会显著扩大它的职责（新增 draggable / layout / text 三类用法）， 建议先把它拆成目录（motion/scope.ts、motion/stagger.ts、motion/drag.ts…）， 否则会变成一个几百行的巨型文件，护栏也就失去意义了。
